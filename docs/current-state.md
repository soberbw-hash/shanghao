## 房间里发生什么

| 操作或条件                         | 软件行为                                                                                                                                                       |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 首次使用                           | 自动录音默认关闭。升级时沿用保存的自动录音选择。                                                                                                               |
| 已开启自动录音，实际加入达到两人   | 包含自己。麦克风和编码器就绪时开始一次录音。空座位不计数。在房间内打开开关也会检查。                                                                           |
| 自动录音中只剩自己                 | 开始五分钟倒计时。有人回来便取消，录音连续。独处满五分钟、离房、切房、连接彻底断开或关闭自动录音时保存。                                                       |
| 手动开始或停止录音                 | 一个人也能录。手动录音由用户结束。手动停止后，本次房间会话不会立即重开。                                                                                       |
| 保存一段录音                       | 录音期间曾有两人就进入转录队列。全程单人可手动转录。自动整理有独立开关。新配置默认游戏结束后处理、开启自动整理。                                               |
| 离开、电话、吃饭、厕所以后手动开麦 | 退出临时状态，同步头像标记；电话模式还要恢复音频设备。只听模式先确认麦克风重连成功。                                                                           |
| 房间纪事                           | 成员可查看当天的房间纪事，贡献自己的语音使用独立的参与状态。北京时间零点切换到新的一天。昨日回顾可以使用服务器保留的摘要样本。                                 |
| 收到新聊天或纪事                   | 列表跟随最新条目，包括用户原先停在列表上方的情形。点击某条消息通知可定位该条消息。                                                                             |
| 昨日回顾                           | 服务端从整天的不同时间取材，结合房间活跃时长、人员和游戏活动。生成完成后更新已打开的回顾。资料稀少时显示实测活动或限定时段，房间在线时长不能用来推断排队时长。 |

静音说话提醒、自动标记游戏、按游戏匹配词汇在后台工作。房间纪事、语音回溯和保存到录音库的录音分别管理生命周期。录音库保存音频、时间标记、文字稿和整理结果。它已移除发布录音摘要的入口。选择云端语音识别会向所选服务发送识别所需的音频，选择云端文字整理会发送相应文本。

## 配置、存储和模块

| 模块                                   | 职责和持久化                                                                                                                                                                                                                                   |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Electron 主进程、preload 和 React 界面 | 主进程管理本机设备、文件和进程。界面经类型化 IPC 访问能力。房间页面使用独立的自动录音生命周期和录音控制器处理开关、成员、计时与收尾。                                                                                                          |
| 录音库与语音记忆                       | 录音目录中的索引记录 `recordingId`、来源房间和可选的 `hadMultipleParticipants`。旧索引与既有录音可读。人数未知的旧文件不会仅因启动软件就新建转录任务。已有任务按检查点恢复。                                                                   |
| 设置与转录                             | `aiTranscriptionProvider` 与 `isAiCloudLocalAssistEnabled` 共同决定云端、云端加本地辅助或自定义语音 API。新配置使用云端加本地辅助，本地模型未就绪时云端先出稿。旧版显式选择的离线模型可继续用。 `isAiAutoOrganizeEnabled` 控制转录以后的整理。 |
| 实时连接与服务端                       | WebRTC 承载媒体；Node.js 信令服务负责加入、状态同步、恢复与中继。客户端用 Rust 原生组件处理 Windows 活动和子进程监督。手机麦克风、DeepFilterNet 降噪、屏幕分享和音频录制各有独立模块。                                                         |
| 房间服务与账号                         | 房间服务存放按北京时间组织的纪事、活动统计与回顾。CloudBase 用于账号；官网是独立的 GitHub Pages 静态站点。用户自有的 API 密钥只在自定义模式需要。                                                                                              |
| 桌面通知                               | 可从好友敲一敲进入房间，从录音或回溯通知打开对应内容。聊天链接由默认浏览器打开。                                                                                                                                                               |

## 模型与资源

实时通话、重连、屏幕分享质量和录音优先。录音期间或实时链路承压时，手动发起的重型转录同样要等待。自动任务按所选转录时机恢复。CPU、可用内存和可读取的 NVIDIA 显存支持调度判断。模型页先显示已有状态，硬件采样在后台更新；依赖、下载及模型配置忙碌各自显示。

Qwen3-ASR 0.6B、1.7B 与共享 ForcedAligner 的 BF16 权重分别约 **1.75、4.38、1.71 GiB**，来自固定版本 safetensors 张量长度。识别和对齐分阶段加载。权重给出冷启动下限，CUDA、激活值和其他程序还会占用空间。本机 RTX 4060 Ti 的一次采样为总计 8188 MiB、可用 2653 MiB，此时 1.7B 连权重也放不下。其他模型的峰值及长录音下的实际峰值仍待实测。默认本地模型为 0.6B；高级、兼容模型与共享组件可以分别展开。[Qwen3-ASR 模型说明](https://huggingface.co/Qwen/Qwen3-ASR-0.6B)

## 五人媒体链路

本轮保留 WebRTC Mesh、逐成员 ICE 恢复及现有 Relay。五人满房每人最多四条对端链路。本机五端测试覆盖后加入、重连、定向音频与媒体转发，20 个有方向的收发组合均有覆盖。这能检查漏建连接、漏转发等错误；跨运营商丢包和真实用户的上行带宽仍需现场数据。

持续屏幕分享时，分享端上行是值得观察的限制。SFU 可以让分享端上传一路媒体，由服务器向接收方转发。LiveKit Cloud 涉及托管流量和房间令牌服务，自托管涉及公网 UDP/TCP、TLS、TURN 容量和故障恢复。若扩大房间人数，或多接收方共享时反复观察到发送端上行饱和，应以相同画质和网络条件比较端到端延迟、丢帧和服务器出站流量。[LiveKit SFU 架构](https://docs.livekit.io/reference/internals/livekit-sfu/) · [自托管网络要求](https://docs.livekit.io/transport/self-hosting/deployment/)

## Windows 包与验收边界

- 正式安装包为 231,109,807 字节（约 220.4 MiB）。本机更新缓存的 SHA-256 与 Release 资产摘要一致，Authenticode 状态为 `NotSigned`。仓库中同名的旧本地候选与正式资产摘要不同，且其展开目录的 ASAR 自检失败。验收正式版使用本机已安装副本和匹配的正式更新缓存。
- 已安装目录审计为 540,008,103 字节，只有一份 FFmpeg。受检的渲染器依赖没有重复打包，未携带其他平台的快捷键预编译插件。正式包通过账号配置、AI runner、原生辅助、字体、降噪、提示音和许可证检查。开发配置进一步排除原生插件构建源码和示例文件。
- 本机普通权限运行正式 3.4.23 的隔离采集探针，得到 3840×2160 视频帧。开发版 Electron 测试覆盖内嵌预览、分离按钮、远端轨道替换后的连续解码。跨电脑分享、游戏独占全屏和长时间弱网使用仍需真实设备验收。
- Windows 更新使用版本元数据、安装包和 blockmap。NSIS 通过安装目录标记限定覆盖和卸载的目标。版本迁移、进程树清理与恢复逻辑有单独回归。用户的正式安装及数据没有用于卸载试验；全新 Windows 用户首次启动耗时、真实安装和卸载、数小时录音仍未实测。
- 发布工作流可从 GitHub Secrets 读取 `WIN_CSC_LINK` 和 `WIN_CSC_KEY_PASSWORD`。配置证书时会校验安装包签名。真实签名验收需要发布者的有效证书。
- 本轮源码包含桌面端与信令服务两部分。要让现有用户获得完整体验，需分别发布新版客户端和部署新版房间服务。
