# 连续按住静音后的延迟恢复

## 原因与修改

`phone-mode-service.ts` 原来把每次按下、松开都排进串行系统音频队列。原生助手枚举、静音／恢复所有端点并写恢复记录比按键事件慢时，会逐次重放已过期的状态。软件端又在恢复请求发出时立即恢复自己的音频状态，连续操作可让系统与软件静音不同步。

本轮保留原生操作的串行顺序，在执行前检查请求代际，跳过所有过期待执行状态；连续触发后只处理最终意图。按下立即关闭软件音频，松开时保持门控，等原生恢复回执确认成功再恢复原麦克风和扬声器快照。恢复过程中再次按住，旧回执不能解除新的静音。

用户意图与暂时仍静音的实际状态分开保存：设备选择变化与休眠恢复只能在用户仍要求开启电话模式时重新静音，不能覆盖一个正在恢复的松开请求。“按一次切换”同样按最新意图切换，恢复失败后可再次尝试恢复。超时请求的迟到错误回执不改写当前状态，原生设备事件错误仍正常报告。

助手拒绝、状态不匹配或崩溃时继续保持软件门控；不因超时、窗口失焦或页面隐藏自动解除系统静音。没有改动实时媒体路径、用户设置或原生恢复记录格式。

## 验证

- 新回归覆盖：系统确认较慢时连续 100 次下键按放、重复 keydown、启动中松开、恢复中再按住、原生拒绝后重试、忙碌时切换、恢复时设备变化／resume、过期回执及原音频四种状态组合。
- 将相同 5 项新回归应用到已提交的修改前服务，4 项失败；修改后全部通过。旧版对照仅在生成夹具中运行，没有覆盖工作区或启动真实助手。日志：`test-artifacts/phone-mode-before-regression.log`。
- 23 项定向检查通过：`test-artifacts/phone-mode-burst-targeted.log`。真实 `PhoneShortcut` 下键解析和服务命令路径接模拟助手，真实 Renderer audio store 在隔离环境核对静音快照。
- 完整 smoke：951 项，950 通过、1 跳过、0 失败；`test-artifacts/phone-mode-burst-smoke.log`。
- 类型检查、对应 ESLint、格式和架构预算棘轮通过；普通构建通过。日志：`test-artifacts/phone-mode-burst-typecheck.log`、`test-artifacts/phone-mode-burst-build.log`。
- 五人音频 20 条有向回退链路与五人真实 WebRTC 自动化媒体恢复检查通过；`test-artifacts/phone-mode-burst-five-audio.log`、`test-artifacts/phone-mode-burst-five-media.log`。这些是隔离自动化，不是五台设备听感。

## 边界

本轮修复位于 Main，需要新主进程／新安装包生效。没有发布、打包 EXE、部署或改版本号。没有运行会改变真实系统音频的 `verify-phone-audio.mjs`，也没有修改用户真实静音设置。原生驱动延迟、硬件失去 keyup、真实游戏前台按键及已安装版仍需新产物实测；自动测试不能证明所有 Windows 驱动环境均不会延迟。
