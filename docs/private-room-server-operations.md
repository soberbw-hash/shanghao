# 私人房间服务器操作说明

适用于 v3.4.0 私人房间实现。本文描述操作顺序，本身不代表服务器已经部署；发布和部署必须有用户在本次任务中的明确授权。

## 存储与账号

- 正式环境使用已配置的账号后端及 HTTPS / WSS；服务端核验 token 后决定用户身份和房主权限。未经认证不能操作房间。
- 设置 `ROOM_DIRECTORY_FILE` 指向服务账号可读写的持久文件，例如 `/var/lib/shanghao/private-rooms.json`。若没有该变量但设置了 `CHAT_HISTORY_FILE`，目录默认存为其路径加 `.private-rooms.json`。
- `NODE_ENV=production` 且两个路径都不存在时拒绝启动。不要把目录放进临时目录、版本解压目录、容器临时层或会被下次部署替换的目录。
- 当前目录存储是**单进程写入**。不要同时运行两个实例写同一个文件；扩展到多实例前必须设计共享事务存储，不能拿复制 JSON 当并发协调。
- 目录保存永久 RoomID、频道号、房主、名称、图标、封禁和删除冷却期；在线成员与媒体连接不持久化，重启后在线数从零恢复。
- 目录及备份仅服务账号和管理员可读；检查父目录权限。文件损坏或未知版本时保留原文件、停止写入并恢复可验证备份，不以空目录掩盖错误。

## 部署顺序

1. 先记录当前服务版本、启动配置与所有持久化路径。停服后备份房间目录、聊天、收藏及房间报告文件，校验备份能读取；不要输出 token 或密钥。
2. 部署服务端代码，设置持久化路径，并保持现有账号、TURN、Relay、TLS 和手机麦克风配置。反向代理应将 `/api/rooms` 及其子路径转发至同一服务端，不缓存鉴权响应。
3. 在隔离测试账号上检查创建、零前缀频道号查找、五人容量、非房主拒绝管理、踢出与封禁、空房资源释放；重启后检查 RoomID、房主、封禁和频道号不变。
4. 确认旧客户端的版本门禁与错误反馈。正式私人房间入口不再支持固定 `main` / `side` 加入；保留旧数据读取不代表旧客户端仍能加入新房间。设定对应 `requiredClientVersion`，再发布兼容客户端，不能靠版本号仍写 3.3.1 推断线上已经兼容。
5. 客户端遇不支持 `/api/rooms` 的旧服务器会显示需要升级服务器，不能退回固定房间或创建另一个本地身份。服务器先升级、客户端后发布。
6. 发布后按真实设备检查房间加入、切换、录音、聊天、分享和手机麦克风远端声音。自动化 HTTP/WebSocket 或五人媒体测试不能替代这一步。

## 回退与身份保护

- 回退程序前停服，避免旧进程与新进程同时写文件。只替换程序，保留持久化路径及当前数据；不要把旧备份覆盖新产生的用户资料。
- 旧服务端不具备私人房间入口时，新客户端应明确不可用。保留目录直到采用有校验的迁移方案，不能靠“回退到一号房”伪装恢复成功。
- 频道号只是查找入口，不是密码；房间内部存储键只能用 RoomID。冷却结束后相同频道号的新房间必须获得新 RoomID，不能附带旧房间的聊天、报告或权限。
- 本地最近与收藏按服务器和账号隔离；失效记录可以显示不可用，不自动映射至重复使用的频道号。删除房间不会删除用户已保存的录音。

## 本地定向验证

从仓库根目录执行：

```powershell
corepack pnpm --dir apps/desktop exec tsx --test tests/private-room-directory.test.ts tests/private-room-signaling.test.ts tests/private-rooms-client.test.ts
node scripts/check-architecture-ratchet.mjs
```

这些测试创建独立临时目录和本地服务，退出时仅删除测试自己创建的目录。真实服务配置、账号资料、录音、模型和安装包不参与测试。
